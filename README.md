# LocalDoc AI（CLI版＋GUI版）

PDFを**外部に送信せず**、自分のPC（GPUなし）の中だけで処理して、**原文を読む負担を減らす**ローカルツールです。

読まずに済ませるためのツールではありません。長い資料を前にして「何が書いてあるのか」「どこを読めばいいのか」を短時間でつかみ、そのあと**原文と読み合わせて確かめる**ための、読む前の地図です。そのため、出てくる文にはすべて原文のページを付け、原文で確認できない内容は表示しません（仕組みは下の「設計の判断」）。

## このツールの位置づけ

- **目的**: 20〜50ページほどの資料を、読み始める前に概要・主要な点・読者がやることをつかみ、どこを原文で読むかを決められるようにする。
- **やらないこと**: 原文の代わりになること。AIの出力は、原文を読む手がかりであって、結論ではありません。大事な点は必ず原文で確認してください。
- **優先すること**: 速さ ＞ 概要レベルの質。ただし、**信頼性は情報量より優先**します。原文にない内容・意味が変わった内容を出すくらいなら、その記述を出しません。
- **外に出さないこと**: 資料の中身は送信しません。ディスクにも保存しません（利用者が「コピー」「保存」を押したときだけ）。動作にネット接続は要りません（モデルの取得時だけ使います）。

企画書の **Phase 1（コマンドライン版）**・**Phase 3（GUI版・PySide6）**・**Phase 4（Windows 向け配布zip）** があります。配布zipの作り方は「3.5 配布版（zip）」を参照してください。

## 出力の内容

- 高速モード: 見出し・冒頭段落・数値を含む箇所など「重要そうな部分」だけを選んで要約（概要把握向け）
- 詳細モード: 全文を分割して要約し、統合する階層的要約
- 「何が書いてあるか（概要・主要ポイント）」と「読者が何をすればいいか（やること・手順）」を**別の節**で出す。「やること・手順」は**モデルに書かせず**、原文から機械的に抜き出した、読者への明示的な作業指示だけを載せる。無ければ「**該当なし**」と表示する（実験・調査・事例の手順の説明は、作業指示として扱わない）
- 実習書・マニュアルなど、課題や手順が命令形で書かれた資料では、**課題カード**を出す: 【課題N】ごとに「やること（指示文）／条件／手順（①②…）／コマンド／確認・提出」を、**プログラムが原文からそのまま**抜き出して並べる（モデルを使わないので速く、書き換えの誤りが無い）。目次に載っているのに指示文が見つからない課題は注意として表示する
- 概要は200〜350字、主要ポイントは5〜8項目を目安にする（内容が少ない資料では無理に満たさない）。原文で確認できなかった記述は**表示せず**、件数を「処理上の注意」に出す
- すべての主張に、**プログラム側で検証した**根拠（ページ）を付ける。モデルが番号を付けなかった文は、プログラムが原文との照合で根拠を探し、「本文との照合による推定」と明示して表示
- 要約中の数値が根拠の原文に実在するかを機械的に確認し、無ければ ⚠ を付ける
- 速度・トークン数・RAMを毎回計測して表示する

## 2. セットアップ（Windows 11）

1. Python 3.11 か 3.12 を入れる（python.org 版。インストーラで **Add python.exe to PATH** にチェック）
2. このフォルダで `setup.bat` を実行（`.venv` を作り、依存を入れます。ネット接続が必要）
   - **PowerShell では `.\setup.bat` と `.\` を付けます**（付けないと「見つかりません」になります）
   - Python 3.12 → 3.11 → 3.13 の順に探して使います。3.14以降だけだと PyMuPDF が入らないことがあります
3. 以降は仮想環境の Python を直接使います（`activate` は不要）。`start.bat` は CLI（`main.py`）、`start_gui.bat` は GUI（`gui.py`）の起動用です。`setup.bat` は GUI 用の PySide6 も入れます（CLIだけなら `requirements.txt` で足ります）
4. llama.cpp とモデルを取得する（**ネット接続を使うのはこの手順だけ**です。PDFの内容は送信されません）
   ```
   .\.venv\Scripts\python.exe tools\setup_assets.py llama
   .\.venv\Scripts\python.exe tools\setup_assets.py model 1.7b
   .\.venv\Scripts\python.exe tools\setup_assets.py model 4b        # 比較用（任意）
   ```
   - 1.7B の公式GGUFは Q8_0（約1.8GB・8bit）のみです。4bit版（Q4_K_M）を試す場合は、コミュニティ版を
     `... tools\setup_assets.py model --repo bartowski/Qwen_Qwen3-1.7B-GGUF --quant Q4_K_M` で取得できます
     （リポジトリの存在は確認済み、ファイル名は未確認）
5. 環境を確認する
   ```
   .\start.bat --check
   ```

## 3. 使い方

### GUI（普通はこちら）

`start_gui.bat` をダブルクリック（またはPDFをこのバッチにドラッグ）。PowerShell なら `.\start_gui.bat 資料.pdf`。

1. PDFをウィンドウへドラッグ＆ドロップ（または「ファイルを選ぶ」/ `Ctrl+O`）。ページ数・文字数・種類が出ます
2. 「高速」か「詳細」を選ぶ（モード名の横に、このPC向けの**目安時間**が出ます）
3. 「要約する」。途中で「中止」できます（モデルのサーバーも止めます）
4. 結果は画面に表示されます。「コピー」（Markdown形式のテキスト）と「保存」は**押したときだけ**書き出します。保存は **PDF（既定）**・Markdown・テキストから選べます（保存ダイアログの形式、またはファイル名の拡張子で決まります）。PDFは画面と同じ薄ピンクの見た目で、フォントも埋め込まれるので、他のPCでも同じ見た目で開けます。「根拠の原文も見せる」「計測を見る」もあります

ウィンドウを閉じる／中止すると、`llama-server` も終了します。資料の内容は、コピー・保存を押す以外では、どこにも書き出しません（覚えるのは、モード・ウィンドウの位置と大きさ・最後に開いたフォルダだけで、Windows のレジストリ `HKEY_CURRENT_USER\Software\LocalDocAI` に入ります）。

起動しないときは、`.\.venv\Scripts\python.exe gui.py` で起動すると、エラーが画面に出ます（`start_gui.bat` はコンソールを出さない `pythonw` で起動します）。

### コマンドライン

以下の `python main.py` は、PowerShell では `.\start.bat` に読み替えてください（同じ引数が使えます）。

```
python main.py 資料.pdf                      # 高速モード（既定）
python main.py 資料.pdf --mode detail        # 詳細モード
python main.py 資料.pdf --mode detail --time-budget 420   # 要約に使う時間の目安（秒、既定300=5分、0で無制限）。超えそうなら重要部分から処理
python main.py 資料.pdf --fast-tokens 2400   # 高速モードの入力量。大きいほど内容を拾うが遅い（既定1500）
python main.py 資料.pdf --model 4b           # 4Bモデルで
python main.py 資料.pdf --sources            # 根拠にした原文も表示
python main.py 資料.pdf --raw                # モデルの生の出力を標準エラーに出す（原因調査用）
python main.py 資料.pdf --extract-only       # LLMを使わず、抽出結果の統計だけ見る
python main.py 資料.pdf > 結果.md            # 保存したいときは自分でリダイレクト
```

- 要約は標準出力、進行状況と計測は標準エラー出力に出ます。`Ctrl+C` で中止できます
- 文書の内容は**自動では保存しません**（ログも一時ファイルも作りません）

## 3.5 配布版（zip）の作り方と使い方

Python を入れていない人にも渡せる、展開して使う形（PyInstaller の onedir）です。**ウェブアプリではなく、デスクトップアプリ**のままで、通信は使いません。

### 作る（開発者・Windows 11 上で）
```
.\setup.bat                  # まだなら（.venv を作る）
.\build.bat                  # llama-server を同梱した zip（約100〜200MB）。モデルは同梱しない
.\build.bat --with-model     # モデル（Qwen3-1.7B Q8_0）も同梱（約2GB）。そのまま完全オフラインで動く
```
- できるもの: `build\LocalDocAI-1.0.0-win64.zip`（と、配布時の改ざん確認用の `.sha256`）
- 内部で `tools\build_package.py` が、PyInstaller（`packaging\LocalDocAI.spec`）→ llama-server の取得（SHA-256検証つき）→ ライセンス全文・ソースコードzipの同梱 → 自己診断（`LocalDocAI.exe --selftest`）→ zip の順に行います。自己診断に失敗すると zip は作りません
- ネット接続を使うのは、llama-server（GitHub）とモデル（Hugging Face）の取得だけです
- 取得済みのものを使うときは `--llama-dir` `--model-file`、llama-server なしで試すときは `--skip-llama`
- **PyInstaller は、作る OS の実行ファイルしか作れません。** Windows 用の zip は、Windows 上で `build.bat` を実行してください

### 渡す（受け取る人）
1. zip を「すべて展開」する（`C:\LocalDocAI` のような場所がおすすめ）
2. モデルが入っていない配布なら `get_model.bat` をダブルクリック（約1.8GB・ハッシュ検証つき。ネットを使うのはこの操作だけ）
3. `LocalDocAI.exe` をダブルクリック
4. 困ったら `check.bat`（自己診断。文書の内容は含まれません）

zip の中身: `LocalDocAI.exe` と `_internal\`（Python・Qt・PyMuPDF・フォント）、`llama\`、`models\`、`使い方.txt`、`LICENSE`、`THIRD_PARTY_NOTICES.txt`、`licenses\`、`source\LocalDocAI-source.zip`（AGPL-3.0 のための、対応するソースコード）。

### 設計の判断
- **onedir にした**: PySide6（LGPL）のライブラリを別ファイルのまま残せて、差し替え可能の条件を満たしやすい。onefile のように起動のたびに一時フォルダへ展開しない（「文書の内容も、アプリの部品も、勝手にディスクへ書かない」方針とも合う）
- **models/ と llama/ は exe の隣**: `config.app_root()` が、配布版では exe のあるフォルダを基準にする（`__file__` は `_internal` の中を指すため）。見つからないときの案内も配布版向けに変わる
- **使わない Qt を入れない**: QtNetwork・WebEngine・QML・マルチメディアなどを除外（サイズが減り、「通信しない」の裏付けにもなる）。UPX は誤検知の原因になるので使わない
- **署名なし**: コード署名の証明書は購入していないため、初回に Windows が「保護されました」と出します（`使い方.txt` に対処を書いてあります）

## 4. 計測と評価

```
python tools\make_sample_pdfs.py                                   # ダミーPDFを samples\ に作る（機密資料不要）
python tools\bench.py samples\lecture_20p.pdf --grid 4,6,8,12 --runs 2
python tools\bench.py samples\lecture_20p.pdf --mode detail --grid 8,8:12 --runs 3 --csv bench.csv
# 既定ではプロンプトキャッシュを無効にして測ります（同じ入力の2回目が不自然に速くなるのを防ぐ）。有効にして測るなら --cache
python tools\eval_facts.py samples\lecture_20p.pdf --mode detail --model 1.7b
```

- `eval_facts.py` は、事実の拾えた数に加え、**確認できず非表示にした記述の数・参照箇所未特定の数・概要の文字数・主要ポイントの数・作業を求める文／課題の数**を出します。信頼性・情報量の改善を実PDFで確かめるときに使ってください（概要は200〜350字、ポイントは5〜8項目が目安）

- `--grid`: 生成スレッド数（`t`、または入力処理用との組 `t:tb`）。P/Eコア混在のCPUでは、全論理コア（16）より少ない方が速いことがよくあります。既定は論理コアの半分（8）で、**根拠のない出発点**です
- `--runs`: 同じサーバーで繰り返します。1回目と2回目以降、連続実行での熱による低下を見られます
- 表示される `total_s` は要約処理のみで、モデル起動時間は含みません（分けて計測）
- 「20ページ・3分」の目標は、自分の実PDFで `bench.py` を回して判断してください

## 5. 構成

```
main.py                  CLI（--check / --extract-only / 要約）
gui.py                   GUIの起動（start_gui.bat から）
app/
  core/    config.py（設定・モデルとサーバーの探索）, errors.py, cancel.py, metrics.py（計測）
  pdf/     extractor.py（PyMuPDF依存はここだけ）, text_processor.py（整形・分割・重要度）
  llm/     engine.py（llama-server の起動・監視・通信）, prompts.py
  summary/ summarizer.py（高速/詳細）, citations.py（参照の検証）, schemas.py（結果と表示）
  pipeline.py            PDF→整形→要約の共通の流れ（CLIもGUIも使う）と、所要時間の見積り
  gui/     main_window.py（画面）, theme.py（薄ピンクの配色・スタイル・アイコン）, worker.py（別スレッドの処理・中止）,
           html.py（結果の表示用HTMLと配色の定義）, export.py（PDF書き出し）, app.py（起動）, assets/fonts/（同梱フォントとそのライセンス）
tools/     setup_assets.py（取得）, bench.py, make_sample_pdfs.py, eval_facts.py
tests/     pytest（LLMなしでPDF解析・要約ロジック・参照検証を単体テスト）
models/ llama/           取得したモデルとllama-server（gitには入れない）
```

見た目は、薄ピンクを基調にした丸みのあるデザインです（見出しとボタンは丸ポップ体、本文は丸ゴシック）。OSが暗いテーマでも、アプリは明るいピンクのまま表示します。色は `app/gui/html.py` の `Colors` に集めてあり、ここを変えると画面と結果表示の両方が変わります。

GUIは、処理をすべて別スレッド（`worker.py`）で行い、画面は固まりません。結果の表示は、PDF由来の文字を**すべてエスケープ**してHTMLにします（PDFの中のタグや画像参照を解釈させない）。

## 6. 設計の判断（採用理由・代替案・トレードオフ）

| 項目 | 採用 | 理由 | 代替と注意点 |
|---|---|---|---|
| PDF抽出 | PyMuPDF **1.26.7 に固定** | 速く、ブロックと文字サイズが取れる。1.26.7は依存なし（wheel 18MB） | 最新の2.xは numpy・onnxruntime・pymupdf-layout を同時に導入する重い構成のため避けた。AGPLなので、配布時は「ソース公開」か pypdfium2 等への置換（`extractor.py` に閉じ込め済み） |
| 推論 | llama.cpp の `llama-server` を子プロセスで起動 | 配布済みの実行ファイルを使える（C++のビルド不要）。落ちてもアプリ本体は無事 | `llama-cpp-python`（同一プロセス）はWindowsでのビルド・wheel事情が不安定。HTTPのオーバーヘッドは要約では無視できる |
| 通信 | 標準ライブラリ `http.client` のみ | 環境のプロキシ設定の影響を受けず、127.0.0.1 以外に出られない。依存が増えない | `requests` / OpenAI SDK は便利だが、プロキシ経由になる事故と依存の増加がある |
| サーバー保護 | 127.0.0.1固定・毎回ランダムなポートとAPIキー | キーは**環境変数**で渡す（コマンドラインだとプロセス一覧に出るため）。Web UI・slots無効 | 同じユーザーで動く他プログラムからの保護には限界がある（企画書どおり、マルウェア対策ではない） |
| 参照の検証 | 番号はモデルに返させ、**対応表はプログラムが持つ** | 詳細モードでは部分要約→元ブロックの対応をプログラムが保持。モデルにページ番号を「思い出させない」 | 存在するが内容が合わないIDは完全には防げない → 数値の実在確認で補う（数値以外の内容の正誤は検証できない） |
| 根拠の推定 | モデルが番号を付けなかった文は、文字2-gramの重なりで原文ブロックを探す（`attribution.py`） | 1.7Bモデルは統合段階で `[S番号]` をほぼ付けないことが実測で分かった。原文の半分以上を説明できない文（原文に無い内容）は推定せず「未特定」のまま | 推定はモデルの引用ではない。言い換えが強いと外れる。表示は「本文との照合による推定」で区別 |
| 課題カード | `tasks.py` が、【課題N】の指示文（〜しなさい等）・直後の条件・①②の手順・プロンプト付きのコマンド行・「※…を受けること」を、文書の並びから機械的に集める。モデルの要約は使わず原文のまま出す（根拠ブロック・ページは正確）。高速/詳細ともモデルに「手順」を書かせない。カードと同じ箇所だけを根拠にした要点は省く | 実測で、1.7Bが書く手順は「管理者権限で操作を実行する」のような断片になり、どこで・どのコマンドで・何のためにが抜け、課題そのものも落ちた | 命令形で書かれていない手順・図や画像の中の手順は拾えない。拾えない手順は「該当なし」または「作業を求める文」（原文の1文ずつ）として出る。論文は対象外 |
| やること・手順 | **モデルに書かせない**。課題カード（下）と、原文の「〜しなさい／せよ／ください／ましょう／すること」で終わる文（1文ずつ・原文のまま・最大10文）だけを載せる。どちらも無ければ「該当なし」。モデルが「手順」を書いても無視する | 実測で、1.7Bは資料に無い作業指示を作ったり、実験の説明を「やること」にしたりした。プロンプトで禁止するだけでは防げないため、出力の経路自体を無くした | 命令形でない指示（「〜が望ましい」など）は拾えない。見つからないことは「指示が無い」ではなく「明示的な指示が見つからない」と表示する |
| 作業を求める文の判定 | `is_directive_sentence`。命令・依頼の語尾で終わり、6文字以上で、過去形でなく、「目的は〜」「目標は〜」のような目標文でない文だけを採用。「目的・目標・ねらい」の節の中は対象外。番号つき手順（①②…）は、過去形が半数以上なら実験の記述とみなして外し、そうでなくても「読者向けの指示文が手順の中・直前にある」か「題が課題・演習・やってみよう等で、実験・調査・事例の題でない」場合だけカードにする。外した手順はページを警告に出す | 実験の手順（「〜を測定した」）や事例の手順を、読者の作業と取り違えないため | 日本語の言い回しの規則なので、取りこぼしも誤採用もあり得る。厳しめに倒してあり、書き方の癖で本当の手順を外すことがある |
| 中身の無い項目の除去 | 「〜を説明する」「〜を示す」だけの項目、日程表、担当・場所などの事務ブロック、6文字未満の断片を、要約の材料や出力から外す | 実測で、こうした項目が概要と主要ポイントを占領した | 規則ベースなので取りこぼし・取りすぎはあり得る（日程表の除外は警告を表示） |
| 原文にない内容の除去 | 要点・概要の各文を、プログラムが原文と照合し、確認できなければ**表示しない**（`summarizer.py` の `_verified_item` / `_verify_section` / `_verify_overview`）。① モデルが付けた参照番号の先の原文と言葉の重なりが0.5未満なら、番号を無視して原文全体から探し直す。② 探しても無ければ捨てる。③ 数値が原文のどこにも無い文は捨てる。④ 「〜しなさい」型の要点は捨てる（作業指示は上の経路だけ）。⑤ 概要は1文ずつ、原文との重なり（0.25以上）と固有語の裏付け（0.6以上）を確認し、通らない文は捨てる。全部落ちたら確認できた要点から作る。⑥ 「記載なし」「特になし」は、そのまま出す。捨てた件数は警告に出す | 小型モデルは言い換えの際に原文に無い内容を混ぜる。プロンプトの注意書きでは止まらなかった | 言葉の重なりでの照合なので、**原文と同じ語を使って作った誤り**は止められない。しきい値（0.5/0.25/0.6）は、実モデルの出力1件（21主張）で調整した値 |
| 意味の保持の検査 | `fidelity.py`（モデルを呼ばない）。要点・概要の各文を、根拠の原文のうち最も近い数文と比べる。① **数値の対象**: 要約で数値と同じ節にある資料中の語が、原文のその数値の節に無ければ「対象がずれた」（例: 原文「大多数の態度が0.7〜0.8の間に収束」→ 要約「態度と本心の分布が0.7〜0.8」の「本心」「分布」）。② 原文に無い因果（〜のため）・条件（〜の場合）・比較（〜より）。③ 原文の「可能性がある」「〜ではない」の脱落、否定の追加。④ 増↔減などの方向の反転。⑤ 「大多数」「一部」の「すべて」への変化。⑥ 原文のどの文にも並んで出てこない「AとB」のひとまとめ。⑦ 根拠のページに無い、資料の他の箇所の語。検出したら、**根拠の原文から最も近い箇所をそのまま取り出して置き換える**（数値を含む文は最大2文まで）。近い箇所が無ければ使わない。概要の文は、要点の一覧とずれていれば捨てる。置換・除外の件数は「処理上の注意」に出す | 追加のLLM呼び出しなしで、数十件の検査が数ミリ秒。小型モデルは言い換えの際に、数値の対象を入れ替えたり、条件・断定の強さを変えたりする | 語の重なりと語句の型で見る検査。原文と同じ語・同じ構造で、意味だけが変わった文は検出できない。しきい値や語句の一覧は、実在の文1,187文で誤検出0件、改変した文で検出率（対象の混入99%・因果の追加97%・方向の反転83%・否定の脱落71%）を確認したが、実モデルの出力では青葉市の1件（21主張）しか見ていない。言い換えを「ずれ」と誤判定すると、原文の文に置き換わる（情報は失わないが、表現が硬くなる） |
| 情報量と正確さの折衷 | 意味のずれを検出して原文に置き換える（上）だけだと、要約が断片的で短くなる。そこで ① 「〜こと」「〜点」で終わる断片は、原文の1文（そのまま・PDFの余計な空白は詰める）に広げる。② 概要は要点を言い換えてまとめた文なので、「ため」「場合」「結果として」のような接続の言い換えは足された因果として扱わず、数値の対象・否定・方向・断定の強さと、原因を言い切る語だけを見る。③ 検証で概要の文が落ちて150字未満になったら、確認済みの要点（結果・結論を優先）を足して200字前後にする（新しい文は作らない）。④ 要点を選ぶとき、結果・結論・貢献を述べる文を少し優先する。⑤ 「本心」「態度」のような資料の中心概念も、数値の対象の検査に使う | 実PDF（態度と本心）で、検査を入れる前の版は情報が多いが数値の対象がずれ、検査を入れた版は正確だが概要が短く要点が断片になった | 断片の拡張で、要点が原文の長い1文になることがある。概要の補完は要点と内容が重なる |
| 根拠として見せる原文 | 画面・PDF・コピーに出す原文は、**抽出済みの本文そのもの**から、その記述と最も言葉の重なる1文を選んで見せる（`pick_snippet`）。モデルに引用を書かせない | 引用をモデルに書かせると、原文にない引用が混じる | 長いブロックでは、根拠の一部分だけを見せる |
| 数値確認 | 主張中の数値（2桁以上・小数・%付き）が根拠ブロックに実在するか | 幻覚の典型を安価に検出 | 漢数字・単位換算は未対応。1桁の整数は対象外 |
| 非思考モード | `--reasoning off` ＋ 各リクエストで `enable_thinking=false` ＋ 出力の `<think>` 除去 | 版や挙動の差があっても二重三重に抑える | 実モデルでの効果は**未確認** |
| トークン数 | 保守的な文字数ベース見積り＋超過時は自動で入力を半分にして再試行 | トークナイザ不要 | 見積りと実測の比を毎回表示（`トークン見積り`）。ずれが大きければ係数を直す |

## 7. 既知の制限

- スキャンPDF（OCR）、パスワード付きPDFは非対応。文字がほとんど取れない場合は警告します
- 2段組みは「左段→右段」に並べ替える簡易ルールです。MuPDFが左右をひとつのブロックにまとめるPDFでは崩れる可能性があります（実PDFでの確認が必要）
- PDF読み込みはアプリ本体と同じプロセスで行います。壊れたPDFで例外は捕捉しますが、MuPDF自体のクラッシュまでは防げません（必要なら別プロセス化）
- 「高速モード」は抜粋の要約です。全文を読んでいない旨を結果に必ず表示します
- 画像内の文字・図表の内容は読みません
- 小型モデルは日本語に中国語（簡体字）の字形を混ぜることがあります。検出したら「処理上の注意」に表示します（自動修正はしません）
- 出力上限で途中切れした部分要約の最終項目は、信用できないため捨てます（警告を表示）

- GUIは、画面の組み立て・読み込み・要約・中止・コピー・保存を、画面を出さない環境（offscreen）で自動テストしています。**Windows実機での見た目（フォント・絵文字の表示）・ドラッグ＆ドロップ・高DPIは未確認**です
- **配布版（zip）の検証状況**: Linux 上で PyInstaller を実際に実行し、できた実行ファイルの自己診断（フォント・PDF読み取り・PDF書き出し・画面の組み立て）が通ることを確認しました。**Windows 上でのビルドと起動、アイコン、SmartScreen の表示、アンチウイルスの誤検知、`get_model.ps1`（PowerShell）の実行は未確認**です。`get_model.ps1` の取得先ファイル名・ハッシュ検証は、このクラウド環境から Hugging Face に接続できないため動かしていません
- `llama-server` が、アプリを強制終了したときにも一緒に終わるか（Windowsのジョブオブジェクト）は**未確認**です（通常の終了・中止・ウィンドウを閉じる場合は停止します）
- 課題カードは、1つの資料（websec演習書）での確認です。他の演習書・マニュアルでは、指示文の書き方の違いで拾えない・拾いすぎることがあり得ます
- 手順の抽出は、実モデルでの検証が**まだ途中**です（部分要約のタグ付けの精度は1.7Bでは揺れる可能性があります）

- **信頼性の改善（原文にない内容の除去・「該当なし」）の検証は、実モデルでは未実施**です。クラウド上でモデルを動かせないため、記録済みの実モデル出力（青葉市の架空資料）に捏造を注入して新旧のコードを比べました（旧: 注入5件すべてが表示された／新: 0件。実在の要点は21→19件で、減った2件は実モデルの言い換えの歪みでした）。**概要の実際の長さ・要点の数・処理時間は、手元のPCで実測してください**（高速モードは入力と出力を増やしたため、約+20秒の見込み）
- 原文の語を**省いた**ことによる意味のずれ（例: 「MCNがもたらす制裁が予測される」を「MCNが予測される」と書く）は検出できません。
- 照合は言葉の重なりによるものです。原文と同じ語を使った誤りは検出できません。意味の保持の検査（`fidelity.py`）も語句の規則なので、否定の脱落は約7割しか検出できません。判定が合っているかは、実モデルの出力でまだ十分に見ていません。また、厳しめの設計のため、原文にある要点を落とすことがあります（その分は「確認できなかった記述がN件」と表示されます）
- 設計の方針：**信頼性を情報量より優先します。** 根拠を原文で見つけられない要点は、近い原文の文で代わりに埋めず、表示しません（モデルが言っていない内容や、文脈の違う文を載せる恐れがあるため）。原文の文への置き換えは、根拠が確認できた要点の意味がずれたときだけです。件数の内訳は「処理上の注意」に出ます。基準を緩める場合も、誤りが増えないことを確かめてからにします
- 番号つき手順は、読者への指示と判断できないものを「やること・手順」に入れません（外したページは警告に出ます）。命令形でない指示は拾えません

## 8. 開発環境

VS Code で、このフォルダを開く → `Python: Select Interpreter` で `.venv` を選ぶ → 左のフラスコ（Testing）で pytest を設定（`tests` フォルダ）すると、テストを実行できます。

```
python -m pytest            # 全テスト
python -m pytest tests/test_citations.py -v
```

偽サーバーを使うテストは POSIX 用で、Windows では自動的にスキップされます。
